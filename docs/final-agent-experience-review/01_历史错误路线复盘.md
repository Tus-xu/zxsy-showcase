## 0. 结论摘要

**一句话**：单调不是“视觉不够漂亮”造成的，而是**回答的“形状”被统一、内容被预设、节奏被固定、学生动作被压缩成点击**四件事叠加；同时验收目标从“像真实智能体”漂移成“像现役系统/像素一致/0 请求/测试通过”，于是每一轮都更安全、更可控，也更像固定流程系统。用户的不满不是局部的，而是产品形态层面的。

五个直接原因（均有证据，详见 §4、§5）：

1. **回答形态同质化**：V5 的所有 assistant 轮次共用同一个 `.reply-panel`（`V5/resources/prototype/preview.js:353`；`preview.css:351`），简答、深度解析、实验、练习、记录视觉重量相同。V6 自己的审计把这一点写成“核心弱点不是缺少基础能力，而是视觉与内容结构的同质化”（`V6修订版/智学数研_V6_市场调研与设计修订.md` §1）。
2. **教学流程被工程化为固定四阶段状态机**：当前演示的状态机头注释直接写“页面只有四个主阶段：读题 → 选方法 → 分步推导 → 订正”（`app/src/offline/showcase/engine.js:5`），并声明“只对已编排的节点与回复作匹配，不假装理解任意输入”（同文件 12–14 行）。这保证了离线可控，也保证了“每轮都像同一个系统在走流程”。
3. **内容不是真实模型回答，而是预生成台词**：V5 的样本由 Codex 预生成（`V5/resources/acceptance/生成与数学审校.md` 第 5 行），V6 明确“文本是预设样本、不支持任意题目和自由追问”（`V6修订版/智学数研_V6_市场调研与设计修订.md` §0），当前演示同样是 7 条预设会话（`主持人手册.md` §1B）。离线本身不是错，错在没有把“预设”组织成有上下文弹性、有边界话术的对话资产，而是组织成了节点脚本。
4. **学生的真实作答被降级为状态标签**：V5 预览把已选答案渲染成灰条“本步作答 · A · -1”（`preview.js:369`；截图 `V5-2026-11-25_S04-feedback.png`），当前演示把首答/订正压缩成“首答 A 订正 C”chip（`CURRENT-2026-11-25_sc-s6-errorbook.png`）。学生看不到“我说过什么”，AI 的承接也失去可见依据。
5. **验收以工程一致性替代产品体验**：11-23 独立视觉 QA 给出 10/10 PASS，11-22 verify-final 给出 PASS，但同一时期三题导学仍未收束（`qa/student-showcase/REPORT.md` §0、§5；`未通过项.md` A3）。这些 PASS 证明“复刻得像、断网稳定”，没有证明“像一个真实智能体”。

**16 条假设判定汇总**：成立 9 条（H02、H03、H04、H05、H10、H12、H13、H14、H16）；部分成立 6 条（H01、H06、H08、H09、H11、H15）；不成立/证据不足 1 条（H07）。逐条见 §3。

### 2.1 版本演进的三个“拐点”

1. **11-22 拐点：从“自造展示”转向“复刻现役”**。这一步在工程上是对的（`ARCHITECTURE-OFFLINE.md`：页面组件原样 fork，后端回放采证响应），但它同时把“现役的缺陷”一起复刻了：三题导学未收束、教师备课全线阻断（`未通过项.md` A1/A3）。演示从“假但完整”变成“真但断”。用户看到的是“真系统原来这么难用”，而不是“成熟的 AI 智能体”。
2. **11-24 拐点：从“复刻现役”转向“在现役里加教学示例”**。为了避免现役断点，团队在对话里加了 7 条本地状态机会话（`ACCEPTANCE.md`）。这解决了“能演完”，但把“真实对话”替换成“编排对话”；用户随即判定它是“更美观的固定流程系统”（D）。
3. **11-25 拐点：从“自己改”转向“用户提供 V5/V6”**。V5/V6 是用户在外部生成的设计包，V6 已经指出 V5 的同质化并做了差异化图示；但两者都是独立预览，不是正式项目。正式项目 11-25 上午仍在“四阶段 + 7 条预设会话”的框架里（`engine.js:5`、`主持人手册.md` §1B）。用户最终看到的仍是“编排过的演示”，于是给出“越来越单调、机械”的总结。

## 3. task §3.1 十六条假设逐条判定

> 判定口径：
> - **成立**：有直接证据（代码/截图/评审）表明该机制存在并造成负面效果。
> - **部分成立**：机制存在，但只覆盖部分版本/部分页面，或效果被其他机制放大/抵消。
> - **不成立/证据不足**：没有证据，或证据指向相反。
> 每条给出证据路径；截图均为已查看。

### H01 是否过度追求极简设计，导致页面越来越空洞

**判定：部分成立。**

- 证据（成立面）：
  - V3 设计规范要求底色 `#fafafc`、无光晕、无彩色底、AI 侧取消气泡（`v3-prototype/DESIGN-SPEC.md` §1.2、§3）；截图 `V3-2026-11-24_01-chat-opening.png` 中 AI 回答直接铺在近白背景上，页面大面积留白。
  - 11-24 整改明确“AI 气泡去底去框、`.ssc` 去外框、题图移出紫色气泡独立成块”（`.workbuddy/memory/2026-11-24.md:37-41`）；`qa/student-chat-showcase/after/sc-s2.png` 中 AI 长回答没有容器边界，阅读像文章。
  - 当前演示 `CURRENT-2026-11-25_sc-s2-knowledge-answer.png` 仍是长文本直接铺底，公式/来源 chip 之外没有回答边界；V6 的“错题空态”页（`V6/resources/v6-screenshots/error.png`）大面积空白，一个空态卡+按钮占据整屏。
- 反证（非全部版本）：
  - 11-21 旧演示首页并不极简（`DEMO-2026-11-21_S01-home.png`：上传卡、三题卡、今日推荐、最近学习，信息密度很高）；11-22 复刻的现役首页也较丰富（`qa/verify-final/shots/live-student-dialog.png`）。
  - V5/V6 又恢复了轻边框（V5 1 px、V6 紫色左线），说明“极简”不是全期统一路线，而是 11-24 整改后的一个阶段。
- 说明：极简本身不是错；错在“用删除容器解决容器过多”，导致短答/长答/练习/复盘失去边界差异。见 §4-F3。

### H02 是否把设计一致性错误地理解为所有回答采用同一种形式

**判定：成立。**

- V5 `preview.js:353` 对每个 assistant 都创建 `div.reply-panel`；`preview.css:351` 定义同一白底、同一边框、同一内边距；`preview.js:369` 连“本步作答”都塞进同一条面板。
- 截图 `V5-2026-11-25_S01-knowledge.png`、`S04-feedback.png`、`S05-dynamic-graph.png`、`S06b-answer-summary.png` 并列可见：知识问答、错因反馈、动态图、练习汇总全部是同一种白卡，差异只在内容。
- V6 文档 §1 明确写出这一点：“`preview.js` 的 `render()` 对全部 assistant 创建同一种 `reply-panel`”“简答、深度解析、实验、练习、记录的视觉重量相近”；V6 用 `data-mode` 分为 `compact/editorial/lab/feedback/practice/record`（`V6修订版/resources/prototype/preview.js:360`）。
- 结论：这是“单调”的最直接机制之一；**一致性应统一字体、色语义、尺度、组件细节，而不是统一容器**（task §9.2 也明确要求）。

### H03 是否把 AI 教学错误地设计成固定业务流程

**判定：成立。**

- 当前演示：`engine.js:5` “页面只有四个主阶段：读题 → 选方法 → 分步推导 → 订正”；`engine.js:907` 文案“把 V1 拆成读题、选方法、分步推导和订正四步，自己走一遍”；`主持人手册.md` §1B 给出逐步操作脚本（“点‘题目看懂了’→‘看导数变号’→……”）。
- V4 期历史截图：`V4-2026-11-25_05-method-cards.png`（两种方法卡+“帮我选”）、`V4-2026-11-25_13-variant-wizard.png`（原题→变式1→变式2→变式3 的向导）。
- V3 原型虽然删除了固定四步的名称（`DESIGN-SPEC.md` §2.1），但其自述“不连接大模型；教学对话是一条……确定性路径，自由提问走关键词路由”（同文件 §5.1），本质上仍是固定流程，只是视觉更接近文档。
- 用户原话：“用户操作与 AI 回复之间存在明显的脚本跳转痕迹”（`.work/task-request.md:48`）。
- 说明：固定流程不是不能用，但不能作为主驱动；它应是“可选教学骨架/兜底”，而不是“每一轮都必须落在某个阶段”。

### H04 是否让学生的大量操作退化为按钮点击

**判定：成立。**

- 原项目 V4 设计的硬规则是“判定回合的结构化卡出现率 100%”“每一回合的学生应答通道必须是后端下发的结构化 form 载荷”（`[ORIG]/docs/design/student-guided-solving-v4/DESIGN.md` §3.1、§3.2）。这把“对话”变成了“每轮填表”。
- V4 历史截图：方法二选一、选项 A–D、变式卡、错因卡；`V4-2026-11-25_05-method-cards.png` 中“帮我选”本身就是把选择交给系统的按钮。
- 当前演示 `CURRENT-2026-11-25_sc-s5-guided.png`：首答显示为选项 A“你的首答”，下方两个按钮“题目看懂了 /「局部」是什么意思?”；`sc-s6`：选项列表 + “加入错题本”。
- 反证：V3 原型用“两格符号槽 + 自由草稿 + 可拖切点”降低了点击依赖（`V3-2026-11-24_04-workbench.png`、`07-practice.png`），V6 也保留了文字作答与图形拖动；所以“所有操作都退化”不完全准确，但**主流程仍是点击驱动**。
- 结论：这是“机械感”的核心来源之一；低输入形式本身是资产，问题是用它替代了对话，而不是服务于对话。

### H05 是否过度依赖预设脚本和关键词匹配

**判定：成立。**

- 当前 `engine.js:12-14` 明说“只对已编排的节点与回复作匹配，不假装理解任意输入；无法判定时留在原步骤并请学生选一步”。
- `qa/student-chat-showcase/ACCEPTANCE.md:72`：“示例只对已编排选项与少量同义短句作匹配。超出范围的自由输入停在原步骤并提示‘先选一个步骤’。”
- V3 原型自述“自由提问走关键词路由”（`DESIGN-SPEC.md` §5.1）；V5/V6 都是固定分支（V5 §4 的 8 个场景；V6 §3 的 8 个场景）。
- 用户原话：“预设回答有时无法准确对应学生的实际输入”（`.work/task-request.md:49`）；“AI 回答内容过于简单、机械、缺乏上下文承接”（同文件 43）。
- 说明：离线不联网、不调模型是合理约束；问题在于“关键词匹配”被当成“理解”，而不是“明确的覆盖范围 + 自然的边界承接 + 多表达模板”。见 §4-F5。

### H06 是否只增加局部数学组件，却没有改善整体智能体体验

**判定：部分成立。**

- 成立面：V4 的交互形式目录有 16 种（`DIAGNOSIS.md` §2.1），但真实会话 17 张交互卡只命中 5 种，`binary/numline/figure_*` 为 0；14 张错因卡（同文件）。组件目录没有转化为体验。
- V5 增加了动态图、条件概率、椭圆对照等 13 张 mockups；V6 增加了概率树、椭圆对照、局部峰顶图等 16 张截图。局部数学表达确实更强。
- 反证：这些组件没有解决“对话是否自然”“回答是否有弹性”“学生操作是否是对话”的问题。V6 自己仍说“文本是预设样本，不支持任意题目和自由追问”（`V6...md` §0）。
- 结论：局部组件是有价值的资产（见 §6），但“整体智能体体验”没有被同一套机制改善；用组件数量掩盖了对话质量问题。

### H07 是否将低保真布局图当成了高保真视觉目标

**判定：不成立 / 证据不足（倾向不成立）。**

### H08 是否将竞品的局部特点机械拼接到同一页面

**判定：部分成立（能力清单式拼接，未见视觉照搬）。**

- V5 §2 和 V6 §2 都以表格形式把 ChatGPT、Claude、Manus、Gemini、Kimi、Brilliant、Mathos、Desmos/GeoGebra 的“可移植规则”逐条列出；例如 V5 表格里“ChatGPT 学习模式→先回应关键疑问；Claude 行内图→小图在回答中展开；Manus→只显示真实执行状态；Gemini→快答/引导不同长度；Brilliant→错步解释在原题附近”。
- 这些规则本身合理，但落地后仍被塞进同一个 `reply-panel`（V5）或同一套 8 场景（V6）；结果像“竞品功能清单”，而不是一个统一的产品体验。
- 未发现直接复制竞品视觉的证据；也没有把官方截图当素材使用（本复盘未使用任何竞品官方素材）。
- 结论：不是“视觉照搬”，而是“把多个产品的能力点逐条映射为页面规则，缺少取舍与统一叙事”。这属于拼接式设计思维。

### H09 是否过度参考后台管理系统，而不是成熟 AI 产品

**判定：部分成立。**

- 成立面：V4 的“举一反三”是典型向导（`V4-2026-11-25_13-variant-wizard.png`：变式 1/3 + 选项 + 答案解析 + 步骤条）；V3 的“学习总结”（`v3-prototype/shots/10-summary.png`：统计卡、证据条、错题、下一步）更像报表；当前 `sc-s6` 的错题复盘也是一张表单（题目+首答/订正 chip+选项+加入错题本）。
- 反证：主对话页仍然是聊天式（用户气泡、AI 文本、输入框），不是后台表格；V3 的交互画布也不是后台。
- 结论：**教学状态/学习成果/错题被做成了后台页面**，而主对话没有；这加深了“两套产品拼在一起”的割裂感。

### H10 是否为了去除卡片而粗暴删除所有回答边框

**判定：成立。**

- 用户原话直接描述了这条演化：“AI 回答由早期的过度卡片化，演变成完全删除回答边框，再演变成统一白色容器，始终没有形成成熟的回答视觉体系”（`.work/task-request.md:45`）。
- 11-24 整改：AI 气泡去底去框、`.ssc` 去外框（`.workbuddy/memory/2026-11-24.md:37-41`；`git show ac84f76` 提交说明原文：“`.ssc` 去掉外框与紫底，改为纯内容块”）；`after/sc-s2.png` 中 AI 长回答没有边界。
- 当前 `CURRENT-2026-11-25_sc-s2-knowledge-answer.png` 仍是长回答直接铺底。
- V3 设计规范“AI 侧取消气泡：π AI 导师 + 紫色小标题 + 正文，文档式”（`DESIGN-SPEC.md` §1.2）。
- 结论：该假设成立，且与 H01 互为因果：为了“去卡片/去后台感”删除边界，结果短答失去锚点、长答变成文章。V6 的紫色左线 / V5 的 1 px 边框是更合理的中间态。

### H11 是否为了增加视觉丰富性而堆叠更多无意义卡片

**判定：部分成立。**

- V4 真实会话 17 张交互卡 + 14 张错因卡（`DIAGNOSIS.md` §2.1），每错一次贴一张“概念不清”标签；截图 `V4-2026-11-25_13-variant-wizard.png` 外层卡套内层题卡、选项、答案解析、步骤条。
- V4 的“已作答”提示、阶段徽标、进度条重复表达同一状态（`DESIGN-SPEC.md` §1.1 也列出这些问题）。
- V5/V6 已收敛：V5 一条回复一个轻边界，V6 用 `data-mode` 区分；但当前 `sc-s6` 仍有“首答 A 订正 C”chip + 选项列表 + 加入错题本，信息层级偏表单。
- 结论：V4 时期确实存在“卡片通胀”；V5/V6 不是“更多无意义卡片”，而是“同一种有意义卡片”。两者都是单调，只是机制不同。

### H12 是否让代码结构反过来限制产品表现

**判定：成立。**

- `docs/superpowers/plans/2026-11-24-student-chat-showcase-implementation.md` §1 明确“不新增路由、不新增顶层导航、不改 `useChat` / `DialogView` 的发送契约”；只新增一条 `showcase_stage` 分支；引擎是纯函数状态机（同文件 §2、§3）。
- 当前 `engine.js` 的纪律“只对已编排的节点与回复作匹配”（12–14 行）、“所有产出都是一条 AI 轮次（text + cards）”（10 行）直接限制了回答形态：不可能出现“真实模型式的自由回答”，也不可能出现“无卡片的纯文本短答 + 组件就地操作”的混合节奏（除非修改引擎）。
- `MessageBubble.vue` 只增加一个 `showcase_stage` 分支（`2026-11-24...md` §2），既有分支零改动——这保证了不破坏现役，但也让新体验只能长在旧消息模型的缝隙里。
- 结论：代码结构不是唯一原因，但它是“产品表现被固化”的直接约束。要改体验，必须允许消息协议/渲染层做更大的改造，而不是“只加一条分支”。

### H13 是否不断创建脱离真实项目的新原型

**判定：成立。**

- V3 原型明确“不改正式项目代码”（`DESIGN-SPEC.md` §6），是一个独立单文件 `v3-prototype/学生端V3原型.html`。
- V5 是独立设计包 `V5设计预览.html`（5 KB 入口 + resources），V6 是独立单文件 `V6单文件离线预览.html`（501 KB）；两者都明确“不要把此独立预览直接覆盖实际 Vue 发行包”（V6 文档 §0）。
- 11-24 用户指出“V3 原型样式与演示项目不符，不能整体搬”（`.workbuddy/memory/2026-11-24.md:32`），正是“原型脱离项目”的直接后果。
- 最终任务书 §11 明确“不得重新创建另一个脱离现有演示项目的 V7 或 V8 原型”；§14.4 禁止 V7/V8/V9 循环（`task-original.md`）。
- 结论：这是最明确的一条；原型探索本身有价值，但连续三代原型都没有变成正式项目的可交付形态。

### H14 是否使用工程测试代替真正的视觉和产品审核

**判定：部分成立（不是“没有视觉审核”，而是“审核目标错位”）。**

- 确实存在独立视觉/功能审核：
  - `qa/review-visual/REPORT.md`：41 张整页截图、7 张并排、度量；发现 B1/B2/M1 并复验关闭。
  - `qa/review-functional/REPORT.md`：166 项脚本断言通过、0 BLOCKER、0 MAJOR（收口后）。
  - `qa/student-showcase/vqa/REPORT.md`：10/10 页 PASS。
  - `qa/verify-final/REPORT.md`：PASS，20 页逐屏 11 一致 + 9 数据漂移 + 0 未通过。
- 但这些审核的核心问题是“是否与现役一致/是否断网/是否测试通过”，不是“学生会不会自然使用/是否像真实智能体”。因此出现：
  - `vqa` 10/10 PASS 的同时，三题导学仍未收束（`qa/student-showcase/REPORT.md` §0/§5）；
  - `verify-final` PASS 的同时，用户仍觉得单调（`task-original.md:114`）。
- 用户原话：“大量精力用于编写设计文档、抽象原型和工程实现，但缺少真正的视觉对照与视觉审查”“智能体通过代码检查、构建测试和功能测试来证明完成，却没有证明产品真的美观、自然、具有真实感”（`.work/task-request.md:50-51`）。
- 结论：用户的表述在字面上略过“已有的视觉审核”，但其判断在结果上成立：**验收 gate 没有覆盖产品体验**。这应作为流程根因，而不是否定 review-visual 等团队的工作。

### H15 是否存在主智能体未亲自查看截图就接受子智能体成果的情况

**判定：部分成立（流程证据，无法确认个人主观行为）。**

- 无法从仓库证明“主智能体是否亲自打开过截图”；只能从结果反推：

### H16 是否在方向尚未验证时，同时扩大了大量场景的修改范围

**判定：成立。**

- 11-24 的 chat-showcase 在核心“一条自然对话”尚未验证前，就实现了 7 条会话（S1–S6 + 组合）、20+ 状态机节点、3 道变式、错题本联动（`2026-11-24...md` §2/§3；`ACCEPTANCE.md` V01–V08）。

## 5. 根因分层：为什么“越改越单调”

### 5.1 产品层：目标函数错了

历史验收的第一目标长期是“复刻真实系统/断网稳定/不破坏现役”，而不是“让学生自然完成一次数学学习”。这从 `EXECUTION_LEDGER.md`（“只做现役离线复刻”）、`qa/verify-final/REPORT.md`（20 页逐屏、0 请求、0 pageerror）和 `qa/student-showcase/vqa/REPORT.md`（10/10 PASS）可以清楚看到。工程上越做越稳，产品上越做越像“固定流程系统”。

### 5.2 设计层：把“一致性”理解成“同形”

V5 的 `reply-panel` 是最典型的证据；11-24 的“去气泡/去框”是另一个极端。两者都缺少“回答形态语法”：简答、解析、实验、纠错、练习、记录应该有不同的边界、标题、视觉主体和操作区。V6 的 `data-mode` 是正确方向，但它仍是独立原型，没有进入正式项目。

### 5.3 内容层：预生成台词不是“对话资产”

V5/V6/当前演示都把内容写成“学生说一句 → AI 说一段”。为了离线可控，这是合理的；但内容组织应该以“状态 + 多种表达 + 边界”而非“节点 + 一段台词”为单位。当前 `engine.js` 的 12–14 行直接承认了“只匹配已编排节点”，于是学生只要换一种说法就掉出脚本。用户说的“预设回答无法准确对应实际输入”就是这一层的直接结果。

### 5.4 交互层：每个教学动作都变成表单

V4 的“判定回合 100% 结构化卡”是把教学状态外化为表单的起点；V5 的“本步作答”灰条、当前演示的“你的首答”选项卡是延续。学生不是在“说数学”，而是在“填系统的表”。V3 的符号槽/画布证明低输入形式可以是有效的，但它应该服务于对话，而不是替代对话。

### 5.5 工程层：状态机 + 一条消息分支 = 产品天花板

`engine.js` 的纯函数状态机 + `MessageBubble` 只加一条 `showcase_stage` 分支，使新体验只能长在旧消息模型上。这不是说状态机不该有，而是说它不能是唯一驱动；消息协议需要支持“文本 + 组件 + 事件回执 + 上下文引用”的混合，而不是“每条 AI 消息都是 text + cards”。

### 5.6 组织层：原型速度 > 集成质量，报告 > 看图

V3/V5/V6 三代原型都不是正式项目；每次不满意就“再做一个原型”，比“把现有项目改到位”快，但用户看到的正式项目没有变。验收上，报告/测试/SHA 比“亲自打开截图看”更容易交付；最终任务书 §12 反复强调主智能体亲自看截图，正是对这条组织惯性的纠正。

### 7.4 应该替换

| 旧 | 新 | 理由 |
|---|---|---|
| 状态机作为回答主生成器 | 会话状态 + 内容路由（多模板 + 意图归一 + 边界） | 状态机可保留为分支/刷新恢复，不控制回答形态 |
| 统一白卡/统一气泡 | 6 种回答形态（compact/editorial/lab/feedback/practice/record） | 一致性是字体/色彩/尺度，不是同形 |
| 长文“助教独白” | 先承接学生上一句，再决定长度；简单问题短答 | 真实 AI 对话的节奏来自上下文，不是固定段落 |
| 内部阶段标签/进度徽章 | 学生可理解的最小状态（如“先看这一步”） | 内部状态不是用户需要的信息 |
| 每回合表单 | 文本 + 卡片混合；UI 事件不进消息 | 学生要“说数学”，不是“填系统” |
| 预置台词逐句匹配 | 多表达模板 + 真实内容资产 + 范围说明 | 预设可以有，但不能只有一种说法 |

### 7.5 需要实验验证

| 实验 | 目的 | 最小验证 |
|---|---|---|
| 同一问题 3 种长度/结构 | 证明回答有弹性，不是每条都长文 | A/B/C 三条截图 + 用户走查 |
| 文本 + 组件混合节奏 | 证明组件出现不打断对话 | 一条包含图/练习/来源的完整会话 |
| 组件操作就地反馈、不生成消息 | 证明 UI 与对话分离 | 操作前后消息数不变、组件状态变化可见 |
| 多轮上下文引用学生原话 | 证明“接住了上一句” | 连续 3 轮追问，AI 复述学生原词 |
| 真实模型内容 vs 预生成内容的边界 | 哪些能用预生成、哪些必须实时 | 内容来源标注 + 能力边界页 |

### 7.6 不再扩大

| 项 | 原因 |
|---|---|
| 教师端/科研端改造 | 本轮是学生端体验；不要扩大战线（`task-original.md` §11.1） |
| 新数学模块/题库 | 先把一条主线做深；`task-original.md` §14.3 |
| 在线模型/真实 OCR 接入 | 现场离线，接在线模型会引入不稳定性；V5/V6 也未接 |
| 复杂 3D/动画/更多组件 | 组件不是体验；先解决对话与回答形态 |
| 更多场景 | 7 条已经太多；先证明一条自然 |

## 11. 一句话回答 task §3

**因为过去每一轮都在把“AI 教学”变成“可测试的教学流程”：回答被统一成一种容器、内容被预设成节点台词、学生动作被压缩成点击/状态标签、验收被简化成“与现役一致 + 0 请求 + 测试通过”。工程上越来越可控，产品上就越来越像一个精致的固定流程系统；而真正让智能体显得真实的“上下文承接、回答弹性、对话与组件的自然混合、学生原话被看见”，一直没有成为主驱动。**

本次纠偏的核心不是再做一个更漂亮的原型，而是：**保留现役 fork/离线回放/真实内容/数学组件这些有效资产，停止新原型与统一容器，把回答形态、内容路由、学生作答消息、验收标准四件事改回“真实智能体”的方向**（详见 §7、§8）。
